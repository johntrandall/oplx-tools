# oplx-tools Integration Suite

End-to-end verification that an `.oplx` file generated by `oplx-tools` round-trips correctly through **a real OmniPlan instance running in a Tart VM**. Each fixture is generated locally, pushed to the VM, opened in OmniPlan, exported to CSV / PDF / PNG, pulled back, and diffed against per-OmniPlan-version goldens.

Unit tests verify *structural* correctness (lint codes fire, parse round-trips, enums are case-correct). This suite verifies *behavioral* correctness — does OmniPlan accept the file? Does the scheduler compute the dates we expect? Does the gantt render?

The suite is marked `@pytest.mark.integration` and **skipped by default**. Run with:

```bash
uv run pytest -m integration
```

Baseline / re-baseline goldens after intentional change:

```bash
UPDATE_GOLDENS=1 uv run pytest -m integration
```

Single fixture:

```bash
uv run pytest -m integration -k f02_simple_chain
```

Wall-clock cost: ~10s per fixture (full open + view-switch + 3 exports + scp). 20 fixtures × 10s ≈ 3:30 for the full suite.

## One-time VM setup

The suite assumes the Tart VM `oplx-tools-integration-test` is running and configured. To bring up a fresh VM:

### 1. Clone from base + start

```bash
# If the test VM doesn't exist yet:
tart clone macos-15.7-l3-omniplan oplx-tools-integration-test
tart-vm start oplx-tools-integration-test
```

(In due course we should rebuild from `macos-15.7-l2-dev` + install OmniPlan + sign in with the agent account per `omni-licensing`. The current clone inherits a personal-account license — anti-pattern flagged in `~/admin-technical/inventories/vm-images/macos-15.7-l3-omniplan.md`.)

### 2. Attach VNC

The Tart compositor does not realize document windows for OmniPlan unless a display observer is attached. Without VNC, image exports fail with `Exporting image types of this view is unsupported. (6)`.

From the host:

```bash
open "vnc://admin:admin@$(tart-vm ip oplx-tools-integration-test)"
```

Approve any keychain prompt that appears. The Screen Sharing window may be off-screen — bring it onscreen with:

```bash
osascript -e 'tell application "System Events" to tell process "Screen Sharing" to set position of window 1 to {100, 100}'
```

The VNC window must stay open for the entire test run.

### 3. Grant TCC permissions inside the VM

Open System Settings → Privacy & Security inside the VM:

**Screen Recording** (click `+`, use Cmd+Shift+G to enter paths):
- `/usr/sbin/screencapture`
- `/usr/libexec/sshd-keygen-wrapper`
- `python3` at `/opt/homebrew/Cellar/python@3.14/3.14.*/Frameworks/Python.framework/Versions/3.14/bin/python3.14` (path varies — find the one Homebrew installed)

Toggle all ON.

**Accessibility**:
- `/usr/libexec/sshd-keygen-wrapper`

Toggle ON.

### 4. Accept the runtime "bypass" dialog

macOS 15 Sequoia introduced a second-layer Screen Recording prompt that fires the first time a granted binary tries to capture: *"X is requesting to bypass the system private window picker and directly access your screen and audio."* This appears in the VM's Screen Sharing window as a separate dialog. Click **Allow** when it appears.

### 5. Verify

```bash
cd ~/dev/oplx-tools
uv run pytest -m integration -k f01_minimal -xvs
```

Should pass in ~10 seconds. If it fails with `AppleEvent timed out` or `Exporting image types of this view is unsupported`, the TCC grants or VNC attachment didn't take effect — re-do step 3 or 4.

## How a test run works

```
Per fixture (vm_helpers.run_fixture):
  1. scp <fixture>.oplx → admin@VM:/tmp/<name>.oplx
  2. AppleScript: close every document saving no
  3. AppleScript: open POSIX file "/tmp/<name>.oplx"  (wait 4s)
  4. AppleScript via System Events:
       click menu item "Gantt View" of menu "View" of menu bar 1
     ⟵ required before image exports. Cmd+Opt+2 is the keyboard
       shortcut but cliclick is unreliable without window focus.
  5. AppleScript: export ... as "CSV" with properties {show all rows:true}
  6. AppleScript: export ... as "PDF" with properties {views to include:both views}
  7. AppleScript: export ... as "PNG" with properties {views to include:both views}
  8. scp /tmp/<name>.{csv,pdf,png} → host artifacts dir
  9. Diff against goldens:
       CSV  — byte-equal after normalization
       PDF  — pdftotext output, whitespace-normalized
       PNG  — file-size within ±10% of golden (visual hash is a TODO)
```

## Adding a new fixture

1. Create `tests/integration/fixtures/fNN_<concept>.py`:

   ```python
   from oplx import Project, Scenario, Task
   from ._builders import START

   NAME = "fNN_<concept>"

   def build() -> Project:
       return Project(
           actual=Scenario(
               id="auto",
               start_date=START,
               tasks=[...],
           )
       )
   ```

2. Generate the goldens:

   ```bash
   UPDATE_GOLDENS=1 uv run pytest -m integration -k fNN_<concept>
   ```

3. Inspect `tests/integration/golden/omniplan-<ver>-build-<build>/fNN_<concept>.{csv.txt,pdf.txt,png.size}` — **make sure the content matches what you intended**. The CSV is the easiest sanity check: does it show the right number of tasks? Are the dates plausible given the dependencies?

4. Commit the fixture AND its goldens together.

## OmniPlan version bumps

The golden subdirectory is keyed by `omniplan-<short-version>-build-<bundle-version>`. When OmniPlan updates (intentionally — auto-update is off in the L2 base; you'd have to do this on purpose):

1. Update OmniPlan in the VM.
2. Run `UPDATE_GOLDENS=1 uv run pytest -m integration` — writes a new directory of goldens for the new version.
3. **Diff the old vs new golden directories.** Look for surprises in CSV (scheduler changes) and PDF text (rendering changes). The harness can't tell intentional from unintentional — that's the operator's call.
4. Commit the new golden directory alongside (don't delete the old — they serve as a record of what worked under each version).

## Known generator bugs the suite surfaces

These were found by inspecting the initial baseline goldens — not failures vs goldens, but evidence in the goldens that OmniPlan doesn't see all the tasks we defined:

- **f07_group_with_subtasks**: defined 3 subtasks (Design, Code, Test); OmniPlan's CSV shows only 2 (Code, Test). Design is silently dropped. Likely cause: an interaction between the auto-created `t-1` root group and an explicit group containing user tasks — `_is_subtask_of_any` may incorrectly include or exclude subtasks.

- **f20_complex_real_world**: defined 9 tasks across groups + milestones; OmniPlan's CSV shows only 1 (the Kickoff milestone). Same suspected root cause as f07, amplified.

Both are TODOs for the generator — track in `dev-docs/` or whatever the project convention becomes. The suite's job is to surface; the fix is elsewhere.

## Architecture

```
tests/integration/
├── README.md                          (you are here)
├── conftest.py                        (pytest config — version detection + skip-by-default)
├── vm_helpers.py                      (push / open / view-switch / export / pull)
├── test_omniplan_renders.py           (parameterized over all fNN_*.py)
├── fixtures/
│   ├── _builders.py                   (shared utilities: START datetime, utc())
│   └── fNN_<concept>.py × 20          (each defines NAME + build())
├── golden/
│   └── omniplan-<ver>-build-<build>/
│       └── fNN_<concept>.{csv,pdf}.txt + .png.size
└── artifacts/                         (per-run pulled artifacts — gitignored)
    └── omniplan-<ver>-build-<build>_<timestamp>/
```

`vm_helpers.detect_omniplan_version()` is called once per session and stamps the version into the golden path + the per-run artifacts directory. Two different OmniPlan versions can coexist in `golden/` — each tracked independently.
